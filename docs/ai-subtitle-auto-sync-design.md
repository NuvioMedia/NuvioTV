## AI Subtitle Auto-Sync — Design

### Problem
Addon-provided subtitle files are frequently out of sync with the video (different cut/release), and the existing manual delay slider requires trial and error. This feature automatically computes and applies the correct delay — and, when needed, a correction for gradual frame-rate-style drift across the runtime — by matching **built-in (embedded) subtitle lines** — which are always correctly timed to the video — against the **addon subtitle file's lines**, using an LLM to do the semantic matching.

**This is the optimal approach for AI-assisted subtitle work: the original subtitle language/content is fully preserved (the AI is only used to find a handful of line-to-line matches for timing purposes), and no costly AI transcription/translation of the entire movie or episode audio is ever required — only a few short text snippets are sent to the LLM per sync, regardless of runtime.**

### High-Level Flow

**Anchor 1 — initial sync (foreground, user-visible)**
1. When the user selects an addon subtitle (and Auto-Sync is enabled), the controller temporarily switches playback to a text-based **built-in** subtitle track (`beginTemporaryInternalCueGathering`) so ExoPlayer starts emitting `CueGroup`s for it.
2. As `CueGroup`s arrive, their text is buffered as timestamped "reference cues" (`recordSubtitleAutoSyncSourceCueGroup` → `appendSubtitleAutoSyncCue`), capped at the last 20 lines. A large jump in presentation time (>90s) clears the buffer, since that indicates a seek to a new region.
3. If the built-in track is image-based (PGS/DVB) with no text cues, the cue bitmap is OCR'd via ML Kit (`recognizeSubtitleBitmapText`) as a fallback.
4. Non-dialogue cues (`♪ music ♪`, `[Music]`, `(singing)`, etc.) are filtered out since they rarely have an equivalent line in the addon file.
5. Once ≥5 reference lines are buffered, the addon subtitle file is downloaded and parsed (and cached per-run so repeated attempts/anchors don't re-download/re-parse it), and a window of ±12 lines around the estimated corresponding position is sent along with the reference lines to an LLM (Groq or Gemini, user-selectable, with user-supplied API keys).
6. The LLM is asked to return confident `{source_index, target_index}` pairs (semantic matching, not positional — line counts between built-in/addon subtitles aren't 1:1).
7. For each returned pair, an offset is computed as `builtInCueTime - addonCueTime` (adjusted for the delay already active on the built-in track's *rendered* position). The process retries up to 3 attempts, pooling offsets across attempts until at least 3 data points are collected (or timing out). The final delay is a **robust mean** of all pooled offsets (`robustMeanOfLongs`): with ≤2 points it's just the median; with 3+ points, the median is used only as a reference to reject gross outliers (>450ms away — almost always an OCR/LLM mismatch, not a real value), and whatever remains is averaged for a tighter estimate than the median alone would give. This replaced a plain median once pooling made 3+ point sets common.
8. This anchor-1 delay is applied globally (flat, no rate) to the subtitle renderer and playback is switched back to the addon track (`endTemporaryInternalCueGathering`). The user sees this result immediately — everything below happens invisibly afterward.

**Anchors 2–4 — background drift calibration (invisible, best-effort)**
9. Right after anchor 1 lands, `maybeStartSubtitleDriftCalibration` kicks off a best-effort background pass to detect a linear drift rate (e.g. a 23.976/24/25fps mismatch) on top of anchor1's flat delay, addressing content where a single fixed offset isn't enough across the whole runtime. It's skipped outright for MPV playback and for image-based (OCR-only) built-in tracks, where a second noisy OCR-derived anchor isn't worth the cost.
10. It spins up a second, fully invisible ExoPlayer instance (`TextOnlyRenderersFactory` — no video/audio renderers, its own `PlayerMediaSourceFactory`) and instantly seeks it to up to 3 more target positions, spread across whichever side of anchor1 (toward file start or end) has more usable room, skipping a safety margin near either edge. Because the drift model is position-based rather than wall-clock-based, these anchors are gathered back-to-back without waiting for real playback to reach them.
11. At each target, the secondary player's cues (or nudges to a nearby position if it lands in a quiet/music stretch) are matched against the addon file the same way as anchor 1, pooling up to 2 LLM attempts per anchor (mirroring anchor 1's own pooling, just with a smaller budget since the multi-anchor fit itself now adds redundancy) and reducing pooled offsets with the same `robustMeanOfLongs`.
12. Each time a new anchor is gathered, a line is (re)fit across all anchors so far (ordinary least-squares; reduces to the old exact 2-point solve at exactly 2 anchors). With 3+ anchors, a single point whose residual exceeds 400ms is treated as a bad measurement (bad OCR/LLM match, not genuine non-constant drift) and dropped, then the line is refit; if residuals are still bad after dropping it, the fit is rejected outright and that anchor is discarded, keeping whatever fit already existed. A rate outside a realistic frame-rate-mismatch range is also rejected as a bad match rather than a real drift.
13. Every time a fit is accepted, it's applied immediately: a new flat `subtitleDelayUs` baseline is picked at the current playback position from the fitted line, then handed off to the existing rate + self-anchoring-sentinel mechanism for forward correction (the renderer self-anchors the rate to its own timebase on its next call, since it can't be compared directly to app-side position values). This means the correction can visibly refine 2–3 times in the background as anchors 2/3/4 land — this is expected progressive refinement, not instability.
14. Anything that goes wrong along the way (buffer contention, a session becoming stale because auto-sync was re-run or the track was changed, all target attempts failing, a rejected fit) is fail-safe: it silently keeps whatever fit/delay was already in place rather than surfacing an error, since this whole pass is a best-effort refinement on top of an already-usable anchor-1 result.

### Key Guards / Edge Cases Handled
- **Session/track identity locking**: a session key (`internalTrackKey|addonUrl`) prevents duplicate concurrent anchor-1 runs and remembers completed sessions so re-selecting the same pair doesn't re-trigger unless the user forces a re-run. The background drift calibration has its own session token, checked before every await point, so a stale calibration from a previous run can never clobber a fresh one.
- **Stale cue protection**: switching tracks or addon subtitles clears the buffer so old cues never get matched against a new file.
- **MPV unsupported**: Auto Sync (both anchor 1 and the background drift pass) currently requires the ExoPlayer internal engine; MPV playback shows an explicit "unavailable" message.
- **No built-in track / non-text-only track**: surfaces a clear error instead of silently failing for anchor 1. The background drift pass separately skips itself (silently) for image-based tracks rather than compounding OCR noise across multiple anchors.
- **API key required**: if the selected provider (Groq/Gemini) has no key configured, the request fails fast with a message pointing to Settings.
- **Manual delay/apply always wins**: manually applying a cue or the delay slider clears any active/pending drift rate and cancels an in-flight background calibration, so a manual correction is never silently overwritten later.

### Remote Key Configuration (phone companion page)
`AddonConfigServer` was extended with a small web form (served over the existing local HTTP server) so the user can enter their Groq/Gemini API key and preferred model from their phone rather than typing it with a TV remote. Submitting the form POSTs to `/api/ai-keys`, which persists the values into `PlayerSettingsDataStore` (`subtitleAiGroqKey` / `subtitleAiGeminiKey`, `subtitleAiProvider`, `subtitleAiModel`).

### Settings Additions
New `PlaybackSettingsScreen` / `PlaybackSubtitleSettings` entries: AI provider picker (Groq/Gemini), per-provider API key entry dialogs, and toggles for `autoSyncExternalSubtitles` and `subtitleAiAutoSelect` (auto-trigger vs. manual "Apply").

### Testing
Fully tested on **Google TV on a TCL TV**, with two movies chosen specifically because synced Hebrew subtitles are notoriously hard to find for them: **The Shawshank Redemption** (חומות של תקווה) and **A Bronx Tale**. Testing was done with Hebrew as the built-in reference language. The only path **not** tested is the OCR/image-based subtitle fallback — no available source with an image-only (PGS/DVB) built-in track was found during testing. This fallback is an extreme edge case and is expected to be exercised rarely in practice. The multi-anchor background drift calibration has been exercised on further field testing since anchor 1 alone was first shipped, including cases with genuinely difficult (mismatched-cut) episodes; a debug trace of the fit process (`scheduling:`, `anchor N: ...`, `fit updated with N anchor(s): rate=...`, `discarding anchor...`) is captured for exactly this kind of on-device debugging.

> **Note:** The subtitle overlay currently contains extensive logging (`subtitleAutoSyncLastLlmRequest` / `subtitleAutoSyncLastLlmResponse`, `subtitleDriftDebugTrace`, and related debug status text) to make it easy to follow exactly what the sync process is doing at each step. This was intentional for review/testing purposes — **it should be stripped down or gated behind a debug flag before this ships to production.**
